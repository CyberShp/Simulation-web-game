# 模拟仙府 · SR需求管理入口

需求基线：SR-XF-2026-10-06 v1.0；继承设计基线DB-2026-10-05 v1.2。

本目录将“需要补齐的设计”变为可开发、可追踪、可验收的独立SR，不把建档算成功能交付。SR编号在改名、重排期、跨会话接续时保持不变。

当前前期32项、条件范围2项、远期暂存6项。下一开发迭代是I1“完整小院”，包含共同契约、空间、预制件、自由营造、人物、生产、物流、触控和迁移。I0处理台账和文档一致性；I2–I5是后续工程顺序，不是重新削减用户要求的完整前期范围。

## SR怎样拆分和关联

每项SR描述一个可验收的能力或完整事件链。设计缺口是同一SR的D任务，开发是I任务，验证是V任务，发布交接是R任务，不为设计和实现建立两个不相认的需求编号。缺陷另以缺陷号关联SR，不改已有事实/验收来迁就缺陷。

每项至少记录：稳定编号、标题、范围/优先级、U/R/T来源、规格路径、现状、设计缺口、具体设计交付物、必须行为、需求依赖、AC情景及预期、子任务、状态、责任人/复核人、证据和变更理由。责任人当前待分配，不虚构承诺日期或已分配人员。

## 状态分开记录

| 维度 | 状态 | 进入完成状态的要求 |
| --- | --- | --- |
| 设计 | refinement_pending / draft / ready / blocked | D01、D02完成且有设计/契约审阅证据；必需参数、失败与迁移策略明确 |
| 开发 | not_started / partial / in_progress / implemented | 范围内数据、行为、视觉、UI和恢复接入，不以文件存在或旧能力替代 |
| 验收 | not_verified / in_progress / passed / blocked | 全部必需AC通过并有证据；浏览器、真机、真人、FPS结论分别记录 |
| 发布 | not_released_for_this_sr / not_applicable / released | 发布必须基于已验收代码；记录main与Pages版本并核对线上 |
| 子任务 | todo / in_progress / blocked / done | done必须有证据；前置任务未完成不得开始下一阶段 |
| AC | not_run / passed / failed / blocked | passed必须有实际情景和结果证据，旧测试数量不代替本SR的结果 |

`partial`只是已有能力的基线，不能自动跳过设计或整条链验收。全部实现、全部验收和所需发布达到门槛后才能关闭SR；若仍缺范围内真机/真人验证，应保留未完成状态。更新子任务不自动把SR升为ready/implemented/passed。

## 启动、阻塞和范围变更

1. 读取本SR及来源规格，核对实际代码与依赖契约；为具体任务记录负责人。
2. 完成D01设计交付物和D02审阅，再将design_status改为ready。可使用已有可用契约开始不依赖未完成部分的工作，必须记录所消费的版本和前置。
3. I01开始后按REQ/AC实现并集成；SR依赖表示能力接缝，不能仅凭依赖ID较小就开始。
4. V01逐条登记正常、拒绝、失败、保存重载及适用设备的预期/实际结果；不上传验收截图和过程产物到仓库，保留必要测试脚本与简要结果引用。
5. R01核对源码、运行时、缓存、素材和回滚；文档SR无需改变游戏运行时，登记not_applicable及文档提交。

阻塞需要明确缺失契约、未定规则或失败情景，以及可独立继续的任务；不得把远期世界观、作者未写完姓名或旧审批记录当作当前已有授权的阻塞理由。任务优先级P0–P3是管理排序，区别于06文档的工程阶段P0–P5。

U-94已激活全部40项SR的设计、开发与验收工作；conditional/deferred保留原建档分类，不再代表本轮未授权。它们仍不作为前期依赖；未答的神道王朝两题继续保留选择边界，不能自动采纳推荐。U项若改变根本规则需由用户新指令明确，作者内容与数值按已有授权补齐并标R/T来源。

## 使用与维护

在仓库根目录执行：

```bash
python qa/sr-manager.py list --scope early
python qa/sr-manager.py list --iteration I1
python qa/sr-manager.py validate
python qa/sr-manager.py refresh
```

更新单项任务的示例（实际使用时替换证据，不照抄虚构路径）：

```bash
python qa/sr-manager.py task SR-XF-003-D01 --status in_progress --owner assigned-developer
```

完成任务时用`--evidence`登记真实的设计路径、提交或简要结果；工具拒绝无证据的done和未完成前置。设计/开发/验收/发布整体状态、AC结果和变更理由在registry.json中明确更新后，执行refresh同步派生文档；不要只改单项Markdown或聊天中的状态。

代码提交、实施记录和后续任务标题引用SR-XF-xxx及其AC编号。现有验收ID保留并由每SR交叉引用；旧验收事实只覆盖原代码/设备，不用于自动关闭新SR。
