## 2. 共同边界与作者方案

- U-121：随机门人，同时在籍最多 15，掌门另计，可补招；掌门最高金丹初期，仇敌金丹中期，首篇复仇完成。
- R-40：韩厉川承担上述终局，三责任人身份不变；新篇章门人也按金丹初期封顶；掌门加至多两名自主同行者；普通人才可以支撑通关。
- U-117／U-120：新山院临时落脚后营造主殿；游戏式大窗口、青玉云纹和书写字体，所有主按钮接实际命令。
- 同一人物、位置、时钟、库存和存档；渲染与列表读取不发奖、不重抽人物。
- 世界暂停、后台、关闭不推进；战术暂停只安排动作，服药／布阵／换装仍用实际时间与物品。
- 已完成旧档保持结局；已有人物、资质、门籍、境界、物品与经历保留。内容迁移与结构迁移分开定版本。

先确认本批会改变的具体原则。已经确认的边界可直接消费；作者方案补字段或调参数时保留依据，改变人数、控制权、境界上限、永久死亡或章节终点须重新取得用户决定。

## 6. 多 agent 如何协作

推荐四个角色，按可用并发数执行：

- **主执行／集成**：拥有共用命令、状态根、存档、入口、需求台账与发布。下发当前 ID、状态字段、命令返回和文件归属。
- **剧情与场景**：写人物／事件／物品／路线定义以及归属自己的局部场景；消费主执行提供的接口。
- **养成与战斗或经营**：每批选择一个模块负责人，写自己的规则与配置；B2 偏经营，B4/B6 偏战斗。
- **独立验证／交互**：先审用户操作是否成立，再验证关键边界；若承担 UI 开发，最终复核由另一人负责。

同一个共享文件只分配一名写入者。子任务返回要附真实差异和验证边界；主执行重新检查跨模块接缝后再合并。缺新产品决定时仅等待受影响部分，其他已确认设计继续推进。

## 7. 验证与记录

1. 先用隔离 QA 档检查本批主要操作：页面打开、按钮可用、对象正确、结果可见、保存可恢复。
2. 再跑最相关的规则与存读测试；检查原有开局、人物身份或库存等被改动接缝。
3. 记录失败／拒绝／撤退等本批真正会遇到的分支；组件检查与正常玩家长链分别命名。
4. 更新 registry 的本批来源、证据和真实状态，运行 `python3 qa/sr-manager.py refresh` 与 `validate`。
5. 运行批通过独立验收后按既有流程提交源码与网页；纯设计批同步源码。只将受验的内容写入发布说明。

目标设备为 iPadOS、Windows、macOS 网页。桌面浏览器视口、触控模拟、真机、真人首次体验分别登记。性能样本记录本宗 16 人、额外访客数量、建筑／活动数、视口、实际帧间隔与模拟耗时；不以 Node 耗时替代游戏 FPS。
