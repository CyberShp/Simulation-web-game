## 2. 已有事实与保持的口径

- [58§2](58-GOLDEN-CORE-PRESET-BUILDINGS.md)规定 GC09–12 每院一级4床，四院一级合计16床，按实际入住分期建设并预留升级。16是该布局的一级床位储备。篇章人数口径为15门人加掌门；掌门早期住处沿用主殿房间。
- 现行 `BUILDINGS.house` 每级4床，最高三级，基础成本45灵石、40木、20石。米制住宅为一级6×6米、二级8×8米、三级10×10米；床号为建筑实例下的 `slot:bed:1…N`。GC09沿用 `site:domain:east-residence-1`，GC10–12分别校准为世界坐标(168,60)、(162,40)、(174,40)，详见第12节。
- `capacity()` 保留旧主殿和住宅的标称口径；本批收录另以真实床位和掌门安置判定。`lifeFacility()` 已按入住声明、剩余空床和可达性选择确切目的地，`rest/heal` 继续共用原身体独占规则。
- `prepareFacilityActivity()` 已有真实行走、独占预约、到场才执行和满位等候；`ea-society` 已有无床时较慢恢复（每次现有生活结算恢复0.3精力）。本批复用其时钟和恢复规则，不增加独立睡眠计时器。
- 07§5要求床位不足表现为等待、疲劳与交涉，保留既有人物；成长章程§4要求迁居接受、目的预约和实际到达，旧住处在新住处成立后再释放。39仍为暂存草案，只引用已被58或现行收录采用的口径，不据此接入整套随机求道者系统。

## 3. T-20 住宅安置规则

以下是 U-63/U-167 范围内的作者实施规则。4床/级、15门人、住宅成本、既有恢复速度属于上一节的已有来源，不重新列为新参数。

1. **安置与身体占位分开。** 常住记录只声明住处和待入住床；实际睡眠仍只有原 `facility` 身体活动及 `slot` 预约。一人正常持有一张住床；换床途中可以同时保留一张旧床和一张目的床，目的床不可再次承诺给别人。
2. **收录优先住宅。** 新收录优先选择已完工住宅的合法空床；尚有主殿过渡床时可以沿用，但先保障掌门已有住处或一张主殿床。医庐床和未来客床分别计数。已有主殿住户继续保留原安置。
3. **选择顺序确定。** 已接受的目的床、本人当前合法身体床位、本人可用住床依次优先；需要另找床时，在未分配且未被身体活动占用的床中选择实际可达路径最短者，再以建筑实例ID和床号稳定排序。检查到床脚点的完整路径，不能只检查建筑门口。
4. **新空床不强制搬家。** 新住宅完工提供机会；有效既有住处继续使用。本批不提供批量强派睡眠或一键迁居。因住处失效而寻找替代床由本人现有休息决策触发，下一张床实际到达后才更新住处。玩家可为掌门选择另一张合法住宅床，并由掌门实际走到新床；选择过程不指派门人。
5. **无床不删人。** 既有超额或待安置居民保留身份和所有生活事实；显示缺口，继续已有慢恢复。已住者丢床后先解决其安置，缺口或重新入住过程尚未解决时暂停新增收录。新收录必须能够承诺真实空床。15名在籍上限与床位是否可用分别判断。

永久床位绑定只用于本院住宅安置，不新增私产、房租、权限等级或跨峰制度。玩家可查看住处；门人的工作、学习、出行和是否开始休息仍由既有自主规则决定。

## 4. 数据形状与接口

独立模块为 `src/simulation/ea-residential-housing.mjs`，使用可选根字段。适用于 `srEnabled(s)` 且 `s.spatial.version === 'spatial-metres-1'` 的新版SR米制院落。旧档缺字段时原样校验、恢复，读取不生成安置；在首个正式世界步、收录事务或掌门指定床位的休息事务中调用 `ensureResidentialHousing`，新档也通过相同生命周期建立记录。既有居民的床位保障按此规则生效；新住宅地块的显式开通只控制地面与建位，不决定住宿规则是否适用，也不新增用户开关。

模块直接读取缺少记录的原档时，`view.enabled` 为 `false`，`choose/admission` 返回 `not-enabled`。正式界面对符合上述SR米制条件的存档提供接入前预览时，调用 `residentialProjectionState(s)`，缺字段时用 `structuredClone(s)` 创建独立查询副本，在副本上 `ensureResidentialHousing` 后调用相同查询；副本只按第14节的完整事实检查复用。该临时投影中的 `pending` 只表示可承诺的目的床，不能显示为已入住，也不写回原档或推进时钟。原身体已经执行且脚点、唯一预约均吻合的 `legacy-observed` 才能显示既有占床证据。

提交使用原命令事务的新副本重新执行 `ensure → residentialAdmissionView → reserveResidentialBed(source:admission) → 原名册与身份更新 → validate → 原子提交`。预览床号只是候选，提交必须重新检查；中途失败整份命令副本丢弃。首个正式世界步也可以完成 `ensure`，后续清理使用 `reconcile`。查询副本与正式事务共用相同确定规则，不在 `hydrate/validate/view` 中给原档添加记录。

```js
s.residentialHousing = {
  version: 'residential-housing-1',
  activatedAtTick: 1234,
  recordsByPersonId: {
    'person:lu-zhiwei': {
      personId: 'person:lu-zhiwei',
      home: {
        buildingId: 'building:yunxiu:<existing-id>',
        slotId: 'building:yunxiu:<existing-id>/slot:bed:2',
        atTick: 1234,
        source: 'legacy-observed' // 或 arrived
      },
      pending: null,
      release: null
    }
  }
};
// home/pending 均可为 null；pending 的非空形状：
// {buildingId, slotId, atTick, source:'legacy-placement'|'admission'|'autonomous-rest'}
// 正常离宗/死亡已由原规则成立后，可保留行但清空home/pending：
// release:{atTick, reason:'departed'|'dead'}
```

示例 `<existing-id>` 是形状占位。建筑、人物均引用现有主表；不保存第二份床坐标、床总数、精力、活动阶段或门籍。`legacy-observed.atTick` 表示本次接入观察到原档已经执行的床位，不反推历史入住日期。`pending` 是安置承诺，实际在途状态从原身体活动派生。

| API | 读写与结果 |
| --- | --- |
| `residentialProjectionState(s)` | 只读兼容入口。已启用时返回原状态；缺字段时返回已安置的独立查询副本，调用者不得提交它 |
| `residentialRestView(s, personId, slotId)` | 只读。仅允许掌门，返回 `{available,reason,reasonCode,candidate}`；重验完整到床通路、活性和入住/身体占位 |
| `residentialBuildingChangeView(s, buildingId, {operation})` | 只读。升级、迁建、拆除前检查该建筑的住处、目的床及身体占位，返回 `{available,reasonCode,reason,residentIds}` |
| `residentialHousingView(s, {personId = null, buildingId = null} = {})` | 只读。返回 `{enabled, version, counts, beds, residents}`；过滤不改变全局计数 |
| `residentialAdmissionView(s, personId)` | 只读。返回 `{available, reason, reasonCode, candidate:{buildingId,slotId}|null, memberLimit:15, memberCount}`；只核对住宿与名额，距离、身份、剧情等仍由原收录入口组合 |
| `chooseResidentialBed(s, personId, action = 'rest')` | 只读。返回 `{buildingId,slotId,reasonCode:null}` 或 `{buildingId:null,slotId:null,reasonCode}`；候选必须落到实际床位。`heal`只用于已有住宅床的兼容占位，医庐治疗选择继续走原规则 |
| `ensureResidentialHousing(s)` | 仅规则启用后的正式世界步、收录或掌门指定床位事务写入；已校验原档的克隆上生成版本及兼容安置，已有记录原样返回；不在hydrate/validate/view中调用 |
| `reserveResidentialBed(s, personId, slotId, {source})` | 仅收录事务、掌门指定床位事务或本人已选择休息的模拟步调用；重新检查所有者、可达、实体床与竞争，写入pending；已有home保持。不可作为任意指派NPC的公开命令 |
| `settleResidentialArrival(s, personId)` | 仅身体活动已经在目标床实际执行时调用；校对唯一身体预约及脚点，将pending变为home并释放旧home；重复调用不改入住时刻 |
| `reconcileResidentialHousing(s)` | 在已有命令收尾/模拟步中处理已成立的离宗、死亡及失效目的地；正式步可为原本没有home/pending的本地居民补上新完工床或返院后的初次安置；不改变人物意愿、生命事实或当前坐标，不在投影或读档中调用 |
| `validateResidentialHousing(s)` | 只校验版本、形状、引用、时刻与唯一声明；缺字段允许旧档，存在未知版本/坏记录则拒绝；不“修好”后再校验 |

`counts`至少提供 `{physical, usable, settled, pending, occupied, unassignedResidents, freeForAdmission}`，各项不简单相加：迁居者可暂时声明两床，身体使用可能属于兼容中的访客。`beds[]`提供 `{buildingId,slotId,position,purpose,usable,reasonCode,reason,homePersonId,pendingPersonId,occupantPersonId,activityPhase}`；`purpose`在本批为`residential`，医庐和客床单独显示而不进入该总数。

`usable`取现有建筑活性门槛（enabled、disabled、condition>0）、完工事实、施工锁及同源门内外通路；部分损坏但condition>0继续按现规则可用。`freeForAdmission`还扣除home/pending声明、其它身体占位以及掌门安置需要；候选人的完整到床路径由`residentialAdmissionView`另行核对。`homeMemberIds`不含掌门，居民床位需求必须明确另计掌门，不能继续用门人数直接减物理床数。已住者失去住床而尚未恢复时，收录返回`housing-shortage`，即使当前存在可供其重新安置的空床，也先完成已有住户的恢复。临时行人挡路由原身体让路规则处理，不修改永久入住身份。

原因码建议：`not-enabled / not-complete / disabled / damaged / construction / no-path / claimed / occupied / no-bed / housing-shortage / roster-full / person-unavailable`。界面文字按实际失败条件产生；查询不更新时钟、床位、事实、活动、随机状态或库存。

## 5. 收录、自主睡眠与竞争接入

1. 陆知微原开局邀请、林长风正式收录及仍可调用的共用收录入口，在住宅规则启用后调用同一住宿校验。现有门籍、赠药、同意和剧情条件继续成立；不用住宿模块代替门籍系统。
2. 显示候选空床只是预览。提交收录时在原命令克隆事务里重验并预留pending，再与原人物加入名册/门籍事实一起提交；失败整体回滚。另一项收录或身体活动占床后，旧预览不能重复使用该床。
3. 预留床不改变NPC的job、学习、承诺或身体活动。其自主选择休息后，`lifeFacility()`与`prepareFacilityActivity()`接收同一确切床号；在现有预约函数中限制候选床，避免“选了有空床的房子、预约时又拿到另一张床”。
4. 人物实际到床并执行才结算入住。途中改变活动可以释放临时身体预约；收录所承诺的床继续保留，待其下一次自主休息。已失效的迁居目的床可在模拟步清理pending，旧home保持。
5. 已在门外等候而没有床号的休息活动，应重新查询其它建筑；有合法床位时改走该床。活动中合法的床与真实治疗不为挑选更近位置而强行打断。
6. 掌门原`masterAction(s,'rest')`建立实际休息活动，允许可选`{buildingId,slotId}`指定自己的目的床。所选床须是住宅rest槽位，建筑与床号须对应且合法空闲；非法选项由原命令事务整体拒绝。换床在途保留旧home；再次选择旧床可撤回目的床承诺。手动休息的实际赴床活动在到达前继续，原自动控制间隔不截断这次行走。
7. `rest/heal`对同一物理床采用同一入住声明判断，同时继续使用原跨用途位置独占检查。医庐病床不成为常住名额；伤匠等访客当前合法身体活动保留，结束后不会自动取得门籍或永久住床。

## 6. 旧档、失效与住宅改建

**接入顺序：** 先用原版本入口完整校验原档并原样恢复 → 到正式世界步或收录命令时克隆 → 在本次合法更新中建立住宅记录 → 校验新增记录及整体状态 → 提交。已启用的新档先校验其原始住宅记录，加载不得重分配床位。未知或重复床号、同床两个承诺者、未来时刻与缺失人物均拒绝，源档原文保留。有效记录所指住处后来停用或断路属于可恢复玩法状态，不因暂不可用而拒载。

- 保留 `person:master`、已入院的 `person:lu-zhiwei`、已入院的 `person:lin-changfeng` 以及所有旧 `homeMemberIds` 的原身份、姓名、门籍、师承、私物、技能、关系与位置。未入院的林长风、陆知微和程问舟等访客继续按原关系；住宿接入不自动收录。
- 接入时先保留已经执行的合法住宅床：把原rest/heal槽位对应到同一物理床的rest槽位，记为`legacy-observed`；原活动、预约、脚点和进度逐字段保留。在途预约只生成对应pending，不写“已入住”。
- 缺少可观察住处的旧居民没有历史入住证据。先保障掌门，再按原`homeMemberIds`顺序确定兼容pending，选现有可达空床；保留其当前工作和行程，实际入床才写home。无法分配者保留空记录并显示待安置。外出居民已有住处保留；缺记录者可等待实际返院再选床，不以缺少当地脚点伪造通路。
- 旧自由布局住宅与主殿继续从实际`facilitySlots`读床，不能因不是GC09–12而删除。GC09建筑与床号沿用；GC10–12只能由正式营造创建。
- 停用、损坏至现行失效门槛、道路阻断：home记录仍保留；新收录不使用该床。本人下一次生活决策寻找合法替代；无替代时原位等待/慢恢复。道路恢复后原承诺可继续，不重置身份或重复登记入住。
- 已成立的死亡/离宗释放住床声明；外出、失踪、被俘或暂时不在场不等于离宗，不能释放住处后再重复安置。处理只引用原人物生命及成员事实。
- 升级保持原床号，新床只在完工后启用。有人居住的升级、拆除和迁建必须沿用成长章程的安全安置前置：先有可达替代并由本人实际迁入，才允许退出旧服务。正式营造入口在扣料和设置施工锁前调用住宅改建检查。无安置时明确拒绝，不先扣材料、清入住或移动患者；本批不新增跨峰迁居制度。
