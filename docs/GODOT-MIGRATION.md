# Godot Web 实施路线

> **当前美术方案 · 2026-10-09 · [U-104](design/DECISIONS.md)：** 用户已确认 Godot 2D、固定斜俯视、统一绘画素材、二维人物动画与连续移动。先按[二维绘画小院](PAINTED-COURTYARD.md)制作一殿、一道、两人的实际 Web 场景；网页美术效果须另行验收，用户认可后再批量扩展。

引擎决策：[U-102](design/DECISIONS.md)；实施选择：[R-31](design/DECISIONS.md)；当前美术决策：**U-104**。本文件安排引擎迁移，不改变 [40 项 SR 交付计划](DELIVERY-PLAN.md) 的需求、依赖和原验收门槛。实际实现、验收和发布状态仍分别以 [STATUS](design/STATUS.md)、[registry.json](requirements/registry.json) 与接手记录为准。

当前先执行[二维绘画小院](PAINTED-COURTYARD.md)：一栋主殿、一段山石道路、两名人物，统一绘画素材由 Godot 二维图层直接使用，网页中验证连续位置、二维动作、缩放、点选和遮挡。制作方案已确认；用户认可实际网页效果后再批量扩展地图、建筑和人物美术。现有 Godot 桥接和历史试验成果保留。

## 目标与共同契约

游戏继续以网页交付，用 Godot 4.6.3 制作二维绘画场景。地图、建筑和人物按 U-104 重新设计；正式玩法的96米山院、2米营造格、0.5米导航精度、封闭建筑完整外观与真实室内活动继续成立；保留已确认的世界、经营、成长、人物自主及全部40项 SR。玩家只直接控制掌门，人物、建筑、库存、活动、事件和战斗仍引用同一稳定身份、位置与世界时钟。镜头、动画和只读页面不推动生产、奖励或 NPC 决定。

本机实施基点为 Godot 4.6.3 stable，项目入口 `godot/project.godot`、脚本 `godot/scripts/`；选择 GDScript、Compatibility 渲染器和单线程 Web 导出。Godot 官方说明 Web 导出使用 Compatibility/WebGL 2，单线程导出可避免线程所需的跨源隔离条件；这些是本批技术选择，目标浏览器和设备仍要实测。[Godot Web 导出说明](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

在规则迁完之前，现有 `dist/ea-opening-sim.mjs` 及其领域模块是唯一模拟权威。`dist/ea-godot-bridge.mjs` 仅传递 Godot 输入请求、公开状态投影和命令结果；Godot 场景不得另存一份可独立结算的人物、建筑或物资，也不得用每帧回调建立第二个世界时钟。桥接请求须带稳定目标 ID、预期修订和可识别的提交结果；同一确认重送只能由既有命令事务规则处理。读档先按当前加载器校验，失败保留原文和可恢复入口；迁移规则所有权时逐项替换写入者与存档映射，不直接改写正式旧档。

构建脚本为 `tools/build-godot-web.py`，Web 导出到 `dist/godot/index.html`；这是构建产物，不作为 main 的手写源码。Godot 预览使用 `godot-preview` 独立存档命名空间，玩家正式三个档位与现行 `dist/index.html` 入口保持原样。G0 达到本批验收后可从 `/godot/` 提供独立网页预览；正式首页只有在替代入口覆盖对应功能与验收、旧档恢复和发布回退均成立后才切换。部署与验收是后续执行动作，本文件不记为已完成。

U-104 二维绘画小院单独使用 `godot/painted_courtyard/courtyard.tscn`、`godot/painted_courtyard/assets/` 和 `tools/build-painted-web.py`，导出至 `dist/painted-courtyard/index.html`。它只有样板场景及观察动作所需的临时状态，不读取或写入正式三个档位，不结算经营资源，不建立并行的游戏世界。它的网页操作和用户审阅只证明对应美术表现；后续与唯一模拟的桥接、真实工位及存档接入须重新取得集成证据。

## 阶段、交付物与退出标准

| 阶段 | 本阶段实际交付 | 退出时必须取得的证据 |
| --- | --- | --- |
| U-104 · 当前二维小院 | 一栋主殿、一段山石道路、两名人物的二维绘画小院；固定斜俯视、统一画风，连续移动与动作，缩放、点选和遮挡。 | 按 [ART-2D 验收表](PAINTED-COURTYARD.md) 实际操作 Web 导出，记录画面、动作、交互及加载结果；用户查看同一构建并认可实机效果后才批量扩展美术。该门槛不替代 G0–G3 玩法验收。 |
| G0 · 引擎与桥接 | 保留已有真实 Godot Web 入口与 JS 桥接基点；点选掌门/人物/建筑、地面移动及一项现有山院操作提交到唯一 JS 模拟，再读取结果更新场景。样板认可后，按相同契约接入新二维资产。 | 构建产物可由网页服务实际加载；新档与有来源旧档在同一身份/坐标/世界刻下显示；点击、移动、一次有效命令、拒绝与重试、暂停及保存刷新续玩逐一实测。只读镜头/点选不改模拟；重复确认不重复扣费。核对浏览器控制台、资产请求、桥接失败提示及与现行状态的结果守恒。此阶段仅证明桥接范围，不声称规则已迁为 GDScript。 |
| G1 · 场景、移动与动画 | 将用户认可的二维绘画小院标准接到真实玩法，承担镜头、真实路径表现、人物/建筑选中、露天活动、封闭屋顶及状态对应动作；沿用当前身份与模拟脚点。 | 真实浏览器逐项观察走路到门/工位、阻路/等待、选中与缩放锚点、横竖和桌面窗口/DPR；用同来源档比较指令前后身份、位置、库存与时钟。记录网页帧间隔、卡顿、加载与内存的测量环境；Node 渲染耗时不能代替网页 FPS。完整专用动作、视觉品质和目标设备尚未测到的部分保持待验。 |
| G2 · 逐 SR 迁规则、完整 UI 与存档 | 按 [原 SR 依赖](DELIVERY-PLAN.md) 每次迁一组共用状态的规则与 UI，明确 JS/GDScript 的单一写入权交接；同一存档格式或有版本的无损迁移进入 Godot 路径。 | 每批列 SR/AC→设计条款→唯一写入者→正常/拒绝/中断/存读/UI；新档、已完成与未完成旧档、坏引用及未知版本按原契约复验，命令幂等、资源归属、人物自主、离屏同钟和结果不重发。桥接尚未迁出的模块继续由 JS 执行，并在证据中标明；迁完一个模块才声明其 Godot 规则实现。 |
| G3 · 完整经营成长与网页交付 | 连续经营、人物成长、场景交互、出行危机、固定复仇与结局后经营贯通；其余 SR 按原范围收口。 | 40 项 SR 各自 D/I/V/R 和 120 条 AC 仍逐项按原门槛核对；新档与支持旧档、正常与失败恢复、长期保存、目标 iPadOS 横竖及 Windows/macOS 网页设备、真人体验和发布版本均有独立证据。正式入口切换前核对完整功能覆盖、存档迁移/回退、线上资源与受验版本一致；未完成项不被阶段名自动关闭。 |

G0–G3 是引擎交付轴；[M0–M8](DELIVERY-PLAN.md) 是 40 项 SR 的需求收口轴。可以在 G1 继续实现 M1/M2 规则，但跨引擎已改动的行为需要新网页证据；不能用两个轴的局部通过数相加宣布整项完成。

## 证据继承与独立复核

既有 JS 公开命令、存档、规则和内容测试仍说明其记录版本的事实，可用作迁移前的对照及未迁规则的回归。旧 Canvas/DOM 截图、鼠标点选、DPR/FPS、浏览器与设备结果不自动证明 Godot 画面、输入、性能或新导出路径；Godot 场景要用实际 Web 构建重做相应检查。保留每条证据的源码/导出版本、存档来源、操作、视口与 DPR、设备、结果和未覆盖边界。

每阶段由实现者交出可复现构建、来源档和结果；独立复核者检查最终差异与实际网页，主执行者再对照 [05 运行契约](design/05-RUNTIME-CONTRACTS.md)、[06 开局验收](design/06-OPENING-ACCEPTANCE.md)、[SR 台账](requirements/registry.json) 决定局部状态。坏档、保存失败和桥接失败均须让原档可读、预览可退出，不能以清档恢复。图稿概念、编辑器运行、Web 导出和正式网页分别记状态。
