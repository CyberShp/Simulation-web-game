# 模拟仙府 · 完整 EA 开发计划

编制日期：2026-10-04（北京时间）。
当前已上线：v0.4.1《余烬立山》基础试玩版。
本计划依据 [EA-DESIGN.md](EA-DESIGN.md)，覆盖此前确定的 P0、P1，以及贯穿各阶段的 UI、UX、存档和质量要求。

**状态说明：除“现状核对”明确列出的能力外，本文均为开发目标。计划写入仓库不代表功能已经完成。**

## 1. EA 要交付什么

交付一款可持续游玩的单机俯视 2.5D 仙侠经营游戏。玩家从遭灭门的修行世家天才开始，亲自控制掌门，在旧别院立足，吸引有自主意志的追随者，积累传承、突破筑基、建立门派、发展初步分峰，并完成第一大篇章的复仇。

核心循环：

1. 掌门行动、探索、交易和调查，获取资源、人才、功法与线索。
2. 建设山院、改善生产与生活、提供学习机会，缓解经营瓶颈。
3. 弟子依据资质、性格、志向、精力、关系与实际机会，自主选择行为。
4. 门人能力与组织规模增长，带来新设施、新传承和新的内部事务。
5. 掌门作出个人与经营决策，承担后果，推进阶段主线。
6. 重要经历持续影响人物；关闭网页后可从最近成功的存档继续。

EA 范围先覆盖炼气到筑基。后续境界、全面战争和庞大的世界地图不作为这一轮的交付前提。

### 1.1 不变的设计边界

- 只直接控制掌门；弟子不提供强制工作、强制学法、强制服丹、指定善恶行为按钮。
- 掌门可以制定制度、提供典籍、设定设施用途与资源预算、发布差事、邀请任职或授业。邀请需要对方愿意接受。
- 天资卓绝不代表绝对上限。更优秀的弟子可以出现，掌门的权威还来自恩义、认同、制度和共同事业。
- 功法有来源、学习前置、相生相克和时间成本；拥有典籍不等于所有人自动学会。
- 开局是共同生活的山院，分峰在人才、传承、人数和资源条件成熟后出现。
- 复仇第一篇章必须真正收束；普通追随者可以不赞同复仇。
- 不做多人联机。联网云存档与多人联机是独立能力，但云存档本轮暂不列为必做项。
- UI、引导、失败反馈和存档随系统一起交付。

### 1.2 本轮内容体量目标

以下是控制开发范围的初始目标，须经试玩调整，不是当前已拥有的数量。

| 内容 | 初始交付目标 | 范围约束 |
| --- | --- | --- |
| 境界 | 炼气至筑基阶段 | 突破材料、功法、修为和风险均有解释 |
| 经营规模 | 重点验证 24–32 名门人 | 先支持稳定的小中型宗门 |
| 建筑 | 约 12–15 种功能建筑 | 优先让布局与岗位有价值，避免重复换皮 |
| 功法 | 约 10–12 部主修/辅修法门 | 至少三条可行路线，早期有适性广的共同传承 |
| 技艺 | 灵植、炼丹、阵法等基础路线 | 不同时铺开大量平行制造系统 |
| 场景 | 别院与若干可探索区域、栖霞旧地 | 复用模块地形，保持区域玩法差异 |
| 主线 | 第一大篇章完整结束 | 包含调查、准备、削弱敌方和复仇 |
| 分峰 | 至少两种可运行的传承方向 | 复杂政治派系后置 |
| 事件 | 先做少量可产生不同后果的完整模板 | 每条必须有触发、行动、发现、处理、记忆与结局 |

## 3. 关闭网页后能否续玩

### 3.1 当前实际行为

可以。当前使用浏览器本机存储保存完整游戏状态，下次在同一设备、同一浏览器及其用户配置、同一网站地址打开，会尝试载入最近成功的存档。

当前保存触发：

- 每 5 秒自动保存。
- 关键操作刷新状态后保存。
- 页面切入后台时保存。
- 页面离开时尝试保存。
- 保留上一份有效快照作为备份。

保存的是资源、建筑、人物修为、功法学习、活动和队列、剧情节点、规则、事件及随机状态等游戏数据。当前不承诺恢复摄像机、上次面板位置等所有界面细节。

当前边界：

- 离线期间不结算收益、不推进剧情、不让门人自行遭遇事故。
- 换设备或换浏览器不会自动同步，需导出 JSON 后在目标浏览器导入。
- 无痕窗口、清理网站数据、禁用持久存储、浏览器回收数据，都可能使本机档不可用。
- 手机强制结束进程、崩溃或断电时，以最后一次成功保存为准，不能承诺精确恢复最后一帧。正常前台定时器工作的情况下，自动保存间隔目标为 5 秒；这不是任何异常情况下的数据损失上限。
- 当前多窗口保护能检测常见覆盖冲突；还需验证同时写入等竞争情况。
- 导出备份保存在用户持有的文件中，与浏览器本机数据分开。

### 3.2 P0 要补到的体验

| 项目 | 目标 |
| --- | --- |
| 启动画面 | 有档显示“继续修行”，标出掌门、门派、境界、游戏日、现实保存时间和版本 |
| 手动存档 | 提供“立即保存”，成功后更新可见时间；失败明确说明并保留导出入口 |
| 多档位 | 初始规划 3 个独立世界档；每个有自己的自动存档与滚动备份，不能互相覆盖 |
| 滚动备份 | 建议保留最近 3 份有效备份和重要版本迁移前备份；避免每帧复制 |
| 章节节点 | 立派、突破、章节结算等关键结果成功提交后生成检查点；奖励只结算一次 |
| 重开与导入 | 先展示即将替换的档案信息；明确选择目标档位；保留可恢复旧档 |
| 异常恢复 | 主档损坏后列出有效备份，显示可恢复到何时；不静默开始新游戏并覆盖旧档 |
| 多窗口 | 同一世界仅一个窗口推进和写入，其他窗口只读或请求接管；显示冲突原因 |
| 版本升级 | 旧档复制后迁移、验证、提交；迁移失败保留原档和导出路径 |
| 回到游戏 | 先恢复完整状态，再显示续玩摘要并允许继续；不在读取途中偷偷推进时间 |
| 提示文案 | 显示“已保存于 13:25”“保存失败，可导出”“另一窗口正在游玩”等真实状态 |
| 长期策略 | 先稳定本机档与文件备份，数据规模增长后评估存储实现；云同步独立立项 |

若将来加入云存档，需要身份识别、服务端保存、冲突选择与备份策略。当前静态托管页面不会自动把玩家存档上传到 GitHub；朋友之间的进度各自独立。

### 3.3 存档验收

S-01：修改资源、营造、学习后刷新/关闭重开，恢复最近成功快照。
S-02：疗伤、学习、炼丹、探索、待选奇遇、待处理事务中断后均可续接。
S-03：奖励领取和突破在保存边界中断，不重复奖励、不重复扣费。
S-04：主档损坏但备份有效，恢复入口可见；主备均坏也保留原始文件供导出。
S-05：存储禁用或已满时，界面不假报保存成功，不覆盖上一份好档。
S-06：双窗口几乎同时保存、切换主窗口、关闭主窗口后接管，均不静默覆盖。
S-07：v1–v4 样例迁移到新结构，资源、人物、建筑和已发生结果可追溯。
S-08：导出、导入及再次导出，游戏关键状态一致；非法或过大文件有清楚说明。
S-09：关闭数小时重开，世界没有离线推进，也不重新抽取已定的随机结果。
S-10：在计划支持的桌面、iOS、Android 浏览器中验证后台、锁屏、恢复与强退边界，并记录实际结果。

## 4. UI/UX 总体改造

### 4.1 视觉方向

保留青绿山水、宣纸、墨色、古铜金与朱砂的仙侠风格，增强可读性和阶段变化。

- 标题使用有古意的字体，正文、数字和长说明优先清晰易读。
- 正文区域有稳定底色，不能让场景纹理穿透到影响阅读。
- 金色提示重要目标与解锁，朱砂提示风险；选中、禁用、警告同时配文字或图形，不能只靠颜色。
- 建筑、人物、道具统一视角、光照、轮廓和比例，减少不同素材拼贴感。
- 早期别院表现出简朴、破损、修复过程；正式立派后再出现牌坊、大殿等仪式感。
- 每栋功能建筑应从轮廓和活动上可辨认；不能只有标签改变。
- 动画可减弱或关闭；音量、音乐、音效分别控制。

### 4.2 信息结构

桌面端优先保留地图的中心空间：顶部简洁资源条，左侧掌门与模式入口，右侧目标/选中详情，底部经营入口。面板可收起，次要信息进入抽屉或详情页。

建议按玩家任务分组：

| 入口 | 主要内容 | 操作边界 |
| --- | --- | --- |
| 掌门 | 状态、行动、修行、装备/术法、个人经历 | 直接控制个人 |
| 营造 | 建筑目录、放置、升级、地形与经营覆盖 | 调整环境 |
| 门人 | 名册、当前行为、意愿、已知经历、关系摘要 | 观察、沟通、邀请 |
| 传承 | 藏书、来源、兼容、学习条件、讲法 | 提供机会与制度 |
| 生产 | 库存、丹房、供给、产出与消耗 | 设经营目标和预算 |
| 山门 | 阶段、职位、门规、事务、分峰 | 组织管理 |
| 山外 | 地图、调查、游历、商路、往来 | 掌门亲往或发布可接差事 |
| 纪事 | 主线、人物大事、已发现线索 | 回顾和追踪 |

早期只展开当下可用项。未达到条件的系统展示获得资格的原因与进度，不堆满永久灰按钮。暂未开发内容只在版本说明中说明；必要的阶段远景应明确标为后续内容。

### 4.3 各页面的具体打磨

| 页面/交互 | 必须解决的问题 | 验收表现 |
| --- | --- | --- |
| 开始与续玩 | 用户不知道能否续档、是否会覆盖 | 首屏区分继续、新开、导入；保存时间清楚 |
| 主地图 | 建筑遮挡人物，标签重叠、点击目标不清 | 选中描边、人物轮廓/遮挡提示、标签按缩放收敛 |
| 掌门控制 | 行走、选中、放置混淆 | 模式指示、目的地/路径、取消方式和到达反馈明确 |
| 营造 | 不知道为何放不了、建完有何用 | 预览占地、材料、条件、预计作用；失败指出具体原因 |
| 门人名册 | 只见数字，不理解为什么不干活 | 当前意图、关键原因、时间投入、精力和已知经历一眼可见 |
| 门人详情 | 信息过多或泄露秘密 | 分“已知信息/观察到的行为/近期经历”；秘密未发现前不展示确切罪证 |
| 传承 | 只显示按钮，看不出学习门槛 | 来源、主辅修、前置、冲突、时间、谁能授业清楚 |
| 门规与事件 | 无法理解制度后果 | 规则生效范围、已知违规证据、处置成本和可预期影响可读 |
| 成长解锁 | 玩家不知道缺什么 | 人数、境界、人才、传承、资源条件分别显示；能定位补足入口 |
| 主线 | 大段文字割裂经营 | 短目标、剧情日志、可追踪线索、阶段回顾；可跳过已读文案 |
| 战斗 | 误触/目标不可辨，失败原因不明 | 范围预警、冷却、伤势、退路和行动反馈明确 |
| 资源面板 | 只知库存，不知短缺成因 | 显示来源、去向、近期净变化；能定位瓶颈 |
| 异常提示 | 错误一闪而过 | 关键错误常驻，可重试/导出/查看原因；普通信息不打断操作 |

### 4.4 操作规则

- 点击选择；达到拖动阈值后才平移地图，释放、失焦、指针取消或切后台都结束拖动。
- 放置模式只影响地图，不能拦截页面外的点击，也不能遗留捕获状态。
- WASD 控制掌门时，输入框、选择框与弹窗不触发角色移动。
- 键盘和触屏都有可见的取消、暂停与返回路径。
- 轻微可逆动作直接执行；拆除、替换档案、重大不可逆选择才要求明确确认。
- 弹窗是否暂停有一致规则；打开菜单后不会因实时重绘丢失选择、滚动位置或输入。
- 排序和筛选、人物切换、定位建筑、寻找任务对象不需要反复退出多层面板。
- 建筑升级后保留选中对象；角色档案更新不重置用户正在读的位置。
- 资源不足的按钮说明“缺少什么”，并在条件满足后及时恢复。

### 4.5 移动端

- 手机支持完整经营与续档流程；横屏改善地图体验，竖屏仍能完成关键操作。
- 顶部优先显示关键资源，更多库存进入展开面板；底部导航采用少量主入口和更多菜单。
- 地图与抽屉按层切换，不能把桌面全部面板挤在一屏。
- 高频点击目标按至少约 44 CSS px 的触控目标设计；最终用真机确认误触。
- 支持安全区域、横竖屏切换、软键盘遮挡和系统返回。
- 不依赖鼠标悬停；长按说明须有普通点击可达的替代入口。
- 测试微信等内置浏览器的表现；如存储或下载能力受限，清楚提示转到系统浏览器并说明档案可能不共用。
- 手机战斗以少量主动技能、清楚预警和暂停规划为目标，不要求复杂多指操作。

## 5. P0 系统工作包

### P0-A 掌门与修行

内容：个人移动与场景互动；修为、精力、伤势；修炼、采集、讲法、学习、游历；炼气到筑基；突破准备与失败后果；少量主动术法和战斗。

决定：境界与资质分开。天资影响学习/成长效率，条件与选择决定能否进阶。掌门闭关与亲自办事会占用同一时间，形成经营取舍。

验收：不依赖调试资源完成筑基；材料来源真实可达；突破、受伤、失败、恢复都有可玩的处理路径；弟子超过掌门不导致数值自动压制或强制叛变。

### P0-B 弟子自主决策

内容：沿用仁心、野心、守信、自律、好奇等人格基础；加入生活需求、修行目标、风险倾向、能力和可用机会。行为覆盖休息、供给、工作、学习、修炼、求药、接差事、沟通与离院。

决策顺序：排除不可执行事项 → 处理紧迫需求 → 权衡志向/制度/关系/资源 → 执行一段时间 → 遇关键变化再评估。持续任务有承诺时间，避免每几秒无意义换岗。

验收：同一人不会同时工作和学习；精力有限；资源不足、道路不可达、无典籍和不愿任职都有可解释结果；不同性格在相同环境下表现有区别；玩家无法用列表按钮强行覆盖选择。

### P0-C 功法、技艺与传承

内容：主修、辅修、基础术法、生产技艺；完整/残缺/待考证典籍；来源记录；境界和基础前置；兼容、精力和学习时长；熟练度、转修、授业能力。

获取途径分批开放：家传 → 交换/购得 → 探索与调查 → 门人带来的传承 → 后期整理改良。

授业：有典籍、允许接触、具备学习基础、有人能讲解分别判断。讲法提供帮助，弟子自己决定参与；不能一次讲法把全员功法写满。

验收：每种关键功法有正常获取路径；不存在拿到全部功法就全员同时精通；相生相克有清楚理由；转修有成本与后果；普通资质仍有可靠的生产或守成路线。

### P0-D 门规、权威与人物后果

内容：取用、典籍、差事、外出等少量核心规则；门人对制度的认同、公平感和风险判断；基础职位；违规的动机、机会、行动、被发现、证据、处置、记忆。

处置先做劝诫、偿还/补偿、限制部分权限、撤职与离院等有限集合。规则不得凭空修改性格；反复偏袒会影响旁观者评价。

人物信息：玩家只看到已知情况，不能通过列表、日志或存档 UI 提前读取未发现事件的确切经过。

验收：善恶行为由条件推动；同一事件不能重复处罚；被发现前不公开真相；处理对后续意愿有持续影响；复杂审判与派系斗争不挤入首批。

### P0-E 生产、生活与布局

内容：现有灵石、木、石、草等资源链；基本生活供给与住宿；生产、修行、学习和维护争用人力；丹药与关键材料消耗；建筑容量与升级；库存预警。

布局：通路、可达性、设施范围、灵气/地形适性先实现一批实际影响。道路、居住、生产、传承区域应该存在取舍，但允许搬迁和修正。

经营：从单纯等待资源增长，转为识别瓶颈、配置环境、改善供给。门人工作受意愿影响，因此保留掌门采集、交易、基础差事等脱困途径。

验收：三种不同发展选择都能推进；无明显无限套利；资源耗尽可恢复；连续游戏无需反复点同一生产按钮；不会因全部弟子学习而永久软锁。

### P0-F 阶段、正式立派与分峰

初始门槛沿用基线示例，并在试玩中校准：

| 阶段 | 条件方向 | 新能力 |
| --- | --- | --- |
| 结庐立足 | 到达别院、伤势逐渐恢复 | 个人采集、简易生产、共同居所 |
| 山院初成 | 约 5 人、基本供给与传承 | 更稳定的讲法、炼丹与差事 |
| 正式立派 | 约 12 人、掌门筑基、传承成型 | 命名/仪式、执事、完整门规、对外身份 |
| 首次分峰 | 约 24 人、两条成熟路线、愿意主持的人 | 峰域、资源预算、授业和归属 |
| 多峰发展 | 人才与运行条件继续成熟 | 跨峰学习与协作的基础 |

人数开放组织规模，掌门境界开放个人能力，门内专家开放专业设施，地形与资源决定能否运行。保留“小而精”的进阶路径，不要求所有内容都强制凑人数。

分峰：玩家划定方向、设施与预算，并邀请主持者；门人根据适性、关系和志向选择归属。分峰与复仇不互相设为硬性前置，避免循环锁与强迫进度。

验收：从共同山院自然过渡到门派；任职需要能力与意愿；两个峰有实际差异和成本；一个峰衰退不会抹除人物能力或造成无法挽救的存档。

### P0-G 游历、遭遇与战斗

内容：掌门亲往与门人自主接取分开；资源探索、遗迹调查、护送/救援、有限遭遇；区域风险、消耗、回报、线索和撤离。

战斗采用规模受控的俯视遭遇：玩家移动掌门，使用少量术法，选择攻击/撤离时机；同行门人自主行动。先做伤势、救助和失败撤离，不把永久死亡设为普通试玩的默认惩罚。

准备阶段的经营必须有用：丹药、阵法、线索、敌方补给与同行者意愿，影响遭遇难度和可选策略。

验收：单靠固定倒计时不能代表完成战斗；玩家行动与经营准备真实改变结果；不会需要微操所有门人；失败有明确原因和恢复路径。

### P0-H 主线、人物记忆和引导

内容：第一大篇章完整；章节目标随经营展开；已读剧情可回顾；关键记忆持久化，一般日志可轮换；首位追随者的经历与复仇态度有连续性。

引导：前几个目标分别教会掌门行动、资源获取、营造、自主门人和传承。重要说明就地出现，可跳过和重看；不要在第一屏用长篇教程压住地图。

验收：玩家知道当前目标与下一步；主线失败不导致无提示卡死；随机访客不成为唯一关键线索来源；复仇结算后可继续经营。

### P0-I 存档、兼容与稳定性

内容与验收见第 3、10 节。该工作包从 M1 开始，每次数据结构或核心循环变化都继续执行，不能到发布前才补。

| 里程碑 | 主要工作 | 同步 UI/UX | 通过后能体验什么 |

| M5 分峰与 P0 收口 | P0-F/E/I：首次分峰、布局价值、经济与存档全面验证 | 峰域、主持者/归属/预算，跨系统导航，完成状态核对 | 小院到正式门派再到初步分峰形成完整循环；P0 可验收 |
| M6 P1 关系与世界 | P1-A/B/C/D：关系深化、个人线、访客、天气与世界反应 | 关系摘要、人物支线、事件因果和世界反馈 | 相同开局能形成不同人物故事和经营处境 |
| M7 EA 整体打磨 | P1-E/F、数值平衡、性能、真机与完整流程回归 | 统一美术/动效/音效、辅助设置、所有页面细节 | P0/P1 本轮范围全部验收，形成可公开长期试玩的 EA |

依赖说明：

- M1 的存档接口和状态版本先稳定，后续模块通过统一入口持久化。
- M2 提供门人与传承基础，M3 才能合理实现执事、筑基和立派。
- M4 的战斗要消费 M2/M3 已存在的准备成果，不能另造一套无关的资源系统。
- M5 基于成熟传承、主持者与供给；复仇结局不会强制玩家立即分峰。
- M6 在 P0 可以完整游玩的基础上增加深度。
- 地图、操作、存档、移动端和性能在每批都验证；M7 是全量收口。

## 9. 每个版本的统一完成标准

每项功能都按以下顺序交付：

1. 规则：明确玩家能控制什么、角色自主决定什么、消耗与后果是什么。
2. 状态：定义数据、存档版本、迁移和重复执行边界。
3. 玩法：正常路径、条件不足、取消、中断、失败和恢复均可运行。
4. 界面：入口、说明、状态、反馈、禁用原因和错误提示齐全。
5. 验证：完成对应黑盒场景与必要的逻辑/存档测试。
6. 试玩：用正常存档和正常资源走通，不以调试数据代替交付。
7. 发布：同时给出实际完成项、已知限制、存档兼容情况和下一批目标。

功能状态统一使用：规划中 / 开发中 / 可验收 / 已上线 / 已知缺陷。不得因为按钮出现或单元测试通过就标记整个系统完成。

## 10. 验收与试玩计划

### 10.1 核心场景

| 编号 | 场景 | 必须得到的结果 |
| --- | --- | --- |
| G-01 | 新玩家首次打开 | 知道扮演谁、当前要做什么、如何保存 |
| G-02 | 不阅读长篇说明完成前几个目标 | 能疗伤、建造、认识门人、看到自主选择 |
| G-03 | 门人资质普通/卓绝且性格不同 | 学习速度、取舍和成长路径存在区别 |
| G-04 | 学习与工作同时争用人力 | 生产会受影响，玩家有可解释的应对办法 |
| G-05 | 功法缺失/相冲/基础不足/精力不足 | 不能无成本学会，说明指出实际原因 |
| G-06 | 私取丹药或私阅禁书 | 行为有动机与机会；发现前隐藏；处理只结算一次 |
| G-07 | 偏袒和公平处置 | 门人态度出现可追踪变化，性格不会瞬间被改写 |
| G-08 | 门人超过掌门境界 | 组织继续正常运行，任职和权威按规则处理 |
| G-09 | 府库资源耗尽或大量门人拒绝工作 | 有个人行动/交易等恢复路径，不永久软锁 |
| G-10 | 达到部分但未达到全部阶段条件 | 知道缺哪项，可从界面定位补足路径 |
| G-11 | 正常获取筑基条件 | 不需要随机刷唯一 NPC 或使用调试资源 |
| G-12 | 复仇准备不足、战斗失败 | 失败原因与代价清楚，可以恢复并调整策略 |
| G-13 | 第一篇章结算 | 仇怨真正收束，人物记忆保留，经营可继续 |
| G-14 | 两个峰路线不同 | 教学、资源、人才与归属有实际差异 |
| G-15 | 人物关键经历跨版本/跨档案导入 | 不被短期日志清理抹除，也不重复触发奖励 |

### 10.2 UI 与输入

U-01：拖动后移出画布、切标签、切后台、弹窗打开、指针取消，均能正常结束拖动。
U-02：用户始终能点击浏览器或宿主界面的其他区域；游戏不留下全局输入捕获。
U-03：缩放、标签遮挡和密集建筑下，仍能选中角色与建筑。
U-04：持续模拟不打断下拉框、输入、滚动阅读和导入流程。
U-05：桌面键盘、触屏、横竖屏都能完成继续游戏、建造、查看门人、处置事务和导出。
U-06：禁用原因、保存失败、读取失败、网络资源加载失败均有可达的处理入口。
U-07：字体、颜色、音效、动画不成为理解系统的唯一方式。

### 10.3 性能与长时间运行

- 建立一个固定参考存档：约 30 名门人、约 40 栋建筑、两条传承、两个峰、进行中的生产/学习/探索与事件。
- 测量输入响应、画面帧时间、每次模拟更新耗时、存档耗时与文件大小，分别记录桌面和移动端环境。
- 初始目标：参考场景桌面接近 60 FPS、移动端稳定 30 FPS，常用操作在约 100 ms 内出现反馈；这些是待实测确认的目标，不是当前性能声明。
- 使用确定性模拟覆盖较长游戏时间，并进行数小时真人会话观察，检查资源溢出、重复角色、死循环、日志膨胀和存档增长。
- 每次重大行为改动验证保存前后继续运行结果一致，防止刷新改变已定事件。
- 普通设备优先保证输入与逻辑正常，允许降低特效和动画密度。

### 10.4 朋友试玩的两轮任务

第一轮（M1/M2 后）：不口头教学，让朋友体验前 15–30 分钟，记录卡点、误触、看不懂的规则、第一次理解弟子自主的时刻，以及关闭重开是否成功。

第二轮（M5 后）：用完整新档或可说明来源的阶段档，验证筑基、立派、复仇和分峰；重点检查是否有“等资源但无选择”“不明原因拒绝”“剧情唯一线索卡死”和“界面找不到入口”。

问题反馈采用简表：版本、设备/浏览器、步骤、预期、实际、截图、是否可复现；玩家愿意时附导出存档。不要要求朋友提供账号密码或其他无关信息。

## 11. 实现组织与范围控制

- 将模拟规则、数据配置、持久化、界面渲染分开维护；先抽离正在修改的模块，逐步减少层层覆盖和共享可变配置。
- 角色、功法、建筑、事件、阶段使用稳定 ID；显示名称可以修改，存档身份不依赖中文名称。
- 把数据版本、游戏版本和资源版本分开；发布时统一资源引用，避免新旧脚本混用。
- 保存随机状态、任务进度和重要事件结果；界面重绘不推进模拟。
- 长期记忆与普通日志分开：关键恩怨、传承和主线结果保留，重复生活日志可摘要或轮换。
- 每批只增加少量能产生玩法差异的内容；先让两条路线有区别，再批量扩写。
- 若某个机制只能靠反复手动派人或强制改性格才能运行，应修改经营条件与自主逻辑。
- 重大数据结构变更在独立分支准备，验证兼容后发布；保留可回退的发布版本和迁移前档案。
- 本计划为文档交付，本次不把后续所有里程碑自动标为已实现。

## 14. 依据与边界说明

代码核对：`dist/persistence.mjs`、`dist/game.mjs`、`tests/persistence.test.mjs`，以及 v0.4.1 的设计文档与已上线行为。核对时间为 2026-10-04。

浏览器平台依据：

- [MDN：localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)：数据可跨浏览器会话保存，但私密会话、来源隔离和存储策略会影响可用性。
- [MDN：pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event)：移动端结束进程等情况下，离开事件不保证触发。
- [MDN：visibilitychange](https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event)：页面切入后台是保存会话状态的重要时机。

上述平台限制用于确定保存策略；测试结果只证明实际覆盖的环境和场景。任何存储实现都不应向玩家承诺断电或强退时绝对零丢失。
